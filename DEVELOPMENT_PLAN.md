# План развития AetherEngine / AetherEditor

Актуализирован 2 ноября 2026 года по текущему рабочему дереву `D:\AetherEngine`, включая staged, unstaged и новые файлы. Реализованы P0, базовый Physics Inspector и исправления опасных мест P1–P2. Этапы M1–M5 сохраняются как план развития и приёмки; наличие отдельных готовых частей не означает завершения этапа.

## 1. Направление и граница прототипа

Сохранить фокус на редакторе и завершить небольшой редактор физических сцен. По коду это уже работающий прототип: сцены открываются и сохраняются, объекты создаются и редактируются, есть история команд, ассеты и симуляция копии сцены. Оценка «почти готов» обоснована для такого назначения. До завершения остаются физика в Inspector, согласование backend и приёмка; полноценный редактор уровней потребует ещё picking и gizmo.

**Ближайший результат:** создать сцену с полом и несколькими примитивами, настроить геометрию столкновений, Static/Dynamic, массу, гравитацию и участие в столкновениях через UI; проверить результат через Play/Stop, отменить изменения, сохранить и открыть сцену повторно. Ручное редактирование JSON для этого сценария не требуется.

Текущий Play запускает физику, используя камеру редактора. Он не запускает игровую логику `smb` и не является полноценным Game Mode. Pause, Step и Game viewport — последующее расширение, а не причина переделывать готовый Play/Stop.

## 4. Архитектура физики: компоненты объекта

**Решение:** Rigidbody и Collider остаются компонентами той же Entity, которой принадлежат Transform и, при необходимости, Mesh/Material. Inspector редактирует данные сцены через команды; PhysicsSystem создаёт backend-тела. Ни панель, ни компоненты не хранят Px/Jolt-объекты.

```text
Entity «Crate»
  Identity + Transform
  Mesh + Material             необязательная визуальная часть
  Rigidbody                   Static/Dynamic, масса, гравитация
  Collider                    форма, размеры, столкновения, sensor
```

Это уже соответствует существующим сериализатору и EntitySnapshot. Введение отдельной «physics entity» для каждого mesh добавило бы синхронизацию двух Transform, владение связью, правила удаления/дублирования и разрешение ID без пользы для текущего сценария.

Отдельная Entity уместна, когда существует самостоятельный объект: невидимая стена, триггерная зона или отдельное тело. Для них достаточно тех же компонентов без Mesh/Material. Связи нужны для joint между двумя телами, дочерних форм составного тела и специальных зон воздействия. Их проектировать позже через устойчивые EntityId, с правилами разрыва и восстановления ссылок, а не через сырые EnTT handles. Иерархии parent/child transforms в текущем редакторе ещё нет.

Для первого этапа сохранить текущий контракт «одно тело — одна Entity — один Collider». **В Inspector выбранного объекта предусмотрен чекбокс Physics** (уточнено 31 октября 2026 года): включение добавляет недостающие Rigidbody/Collider к этой же Entity одной командой; новым Rigidbody по умолчанию давать Static. Уже существующие настройки сохранять. Выключение удаляет оба компонента одной отменяемой командой, сохраняя сам объект, Transform и визуальные компоненты. Undo возвращает удалённые компоненты со всеми настройками; повторное включение после удаления создаёт компоненты с исходными значениями, а не восстанавливает скрытую копию.

Чекбокс отмечен, когда присутствуют оба физических компонента. Неполный набор показывать как неактивную конфигурацию с выключенным чекбоксом: включение добавляет только недостающий компонент, а отдельное действие **Remove incomplete physics** позволяет удалить оставшийся. Без Transform включение недоступно, удаление существующих компонентов разрешено. Во время Play все эти действия заблокированы. Отдельные сущности, связи-указатели и сохранённый флаг `physicsEnabled` для этого не нужны: состояние определяется наличием компонентов.

Позже можно разрешить `Transform + Collider` как неявное статическое тело, а Rigidbody использовать только для движения. Это отдельное изменение контракта PhysicsSystem: сейчас оно не реализовано и для завершения прототипа не обязательно.

## 5. Спецификация Physics Inspector

### 5.1. Первое приращение: существующие поля

| Элемент UI | Данные / поведение |
|---|---|
| Physics: включить / выключить | Чекбокс у выбранного объекта: добавить Rigidbody + Collider / удалить оба компонента; одна команда Undo/Redo. Новый Rigidbody — Static; неполный набор дополняется с сохранением настроек |
| Body Type: Static / Dynamic | Пока отображение существующего `Rigidbody.dynamic`; новый enum не нужен до появления Kinematic |
| Use Gravity | `useGravity`; доступен для Dynamic. Отключение гравитации не делает тело статическим: оно продолжает реагировать на столкновения |
| Mass | `mass`; редактируется для Dynamic, конечное положительное число в общем допустимом диапазоне |
| Shape: Box / Sphere / Capsule | `Collider.type`; рисуются только подходящие поля размеров |
| Box Dimensions | UI показывает полные размеры; запись `size = dimensions / 2`, поскольку текущий JSON хранит half extents. Для куба 1×1×1 требуется `size = 0.5, 0.5, 0.5` |
| Sphere Radius | `radius`, положительное конечное число |
| Capsule Radius / Cylinder Height | `radius` и текущий `height`; полная высота капсулы равна `height + 2 * radius`. Не подписывать существующий height как полную высоту |
| Sensor / Trigger | `trigger`: нет физического отклика на контакт. Сейчас API событий enter/stay/exit отсутствует; поле не обещает готовую игровую логику триггеров |

На этом приращении использовать прежнюю схему сцены v2. Не переименовывать сохранённые поля и не менять их смысл только ради подписей UI. Отдельное редактирование Camera и Material.baseColor делать после физики; существующие значения этих компонентов уже сохраняются, но не все доступны в Inspector.

### 5.2. Тумблер столкновений — отдельная семантика

Добавить `Collider.collisionEnabled`, по умолчанию `true`. Это новое поле и новая возможность backend, а не готовая галочка поверх существующего `trigger`.

- **Collision Enabled = false:** тело сохраняет массу, геометрию для расчёта инерции, движение и гравитацию, но не сталкивается и не выдаёт trigger-события. В будущем отдельно определить участие в scene queries; сейчас общего query API нет.
- **Use Gravity = false:** отключается только гравитация; столкновения остаются.
- **Sensor = true:** при включённых столкновениях форма работает как датчик без физического отклика. Систему доставки событий реализовать отдельной задачей.
- **Physics = false:** оба физических компонента удалены, у объекта нет физического тела. Это отдельный чекбокс от Collision Enabled, который сохраняет тело и отключает только столкновения.

В PhysX/Jolt реализовать одинаковое поведение фильтрации, сохранив интеграцию Dynamic. Простое удаление Collider остановит тело при нынешнем ECS-фильтре и потому не реализует требуемый тумблер.

Для сохранения новой семантики рекомендован явный переход на v3: читатель принимает v2 и v3, у v2 `collisionEnabled=true`, новый writer пишет v3. Старый reader тогда явно отвергнет v3 вместо молчаливой симуляции с включёнными столкновениями. Открытие v2 не перезаписывает файл автоматически; переход происходит при явном Save. Тесты и fixtures обновить одновременно, сохранив отдельные проверки v2. Расширение версий — маленькая целевая миграция, не универсальный framework.

### 5.3. Геометрия и совместимость

Для завершения первого прототипа **сохранить существующие абсолютные размеры Collider, независимые от Transform.scale**, и явно показать это в панели. Предпросмотр обязан рисовать именно эту форму. Иначе автоматическое применение scale изменит физику уже созданных v2-сцен. Local-scaled shapes и Fit to Mesh оставить следующим улучшением с явным режимом/миграцией; отрицательный и неравномерный scale требуют отдельного правила для Sphere/Capsule.

Ось капсулы движка зафиксирована как **локальная X**, вместо ранее предложенной Y: это сохраняет существующую геометрию основного Windows/PhysX-профиля без скрытой миграции v2. В Jolt его Y-капсула обёрнута поворотом shape на −90° вокруг Z; Transform Entity не меняется. Старые сцены, настроенные под прежнюю Jolt-ориентацию, требуют ручной проверки Capsule: одновременно сохранить две прежние интерпретации одного файла невозможно. Preview в M1b должен использовать ось X и `height + 2 * radius`.

Размеры, массу, допустимые значения и геометрию проверять общим кодом на входе из UI/команд/сериализатора. Ошибка должна содержать имя объекта и поле. В backend оставить защитные проверки. Отказ создания формы, включая ограничения конкретного SDK, должен быть виден в Console/Inspector.

### 5.4. История и жизненный цикл

- Переключение Physics (добавление/удаление компонентов) и изменение каждого значения проходят через CommandHistory, используют EntityId и копии данных до/после. Одно переключение чекбокса, как и один числовой drag, создаёт одну запись Undo.
- Обобщить текущие `finishTransformEdit`/pending edit до завершения любых редактируемых компонентов: смена selection, скрытие Inspector, Save, Undo, Play и смена документа не теряют последнюю правку. Escape отменяет незавершённое редактирование там, где это поддерживается UI.
- Duplicate/Delete Undo и runtime clone используют тот же EntitySnapshot. Новые поля существующих компонентов копируются вместе со структурой; сериализатор, сравнения и round-trip проверки расширяются явно.
- Во время Play инспектор остаётся недоступным для изменения. Следующий Play создаёт тела из актуальных авторских данных; горячее изменение физических свойств не входит в этот этап.
- Новые типы компонентов должны добавляться согласованно в сериализацию, snapshot/restore и UI. Пока достаточно явного списка адаптеров; универсальная reflection-система не требуется.

## 6. Последовательность работ

Этапы описывают проверяемый результат, без календарных обещаний. M0 и M1 составляют завершение текущего прототипа; M2 и далее развивают его.

### Автоматические проверки для M0/M1

1. Физические команды: Add/Remove, изменение каждого поля, повторные Undo/Redo, dirty относительно Save, отсутствующая/удалённая Entity, отсутствие истории для no-op; откат объединённой команды при частичном отказе.
2. Сериализация: все физические поля; v2 defaults и v3 round-trip; отсутствие silent reset допустимых значений; отклонение NaN/Inf, нулевых/отрицательных размеров и недопустимой массы до записи.
3. Полный путь: Scene → PhysicsSystem → backend; Static не падает, Dynamic с gravity падает, без gravity не падает, collision off проходит сквозь пол и продолжает движение. Повторить Start/Stop с реальным clearSceneBodies и проверить отсутствие накопленной скорости/тел.
4. Геометрия: Box с известными полными размерами, Capsule с заданной осью/высотой, независимость от визуального scale в legacy-режиме; одинаковые смысловые ожидания для PhysX и Jolt без требования побитовой идентичности траекторий.
5. Ошибки: невалидная форма и превышение лимита диагностируются; неуспешный Play/Stop сохраняет доступ к авторской сцене; новое значение mass корректно влияет и на инерцию.
6. Документ: Save/Discard/Cancel для New/Open/Close, завершение pending edit, отказ записи, закрытие во время Play с dirty edit-сценой, подтверждение Save As. Ошибка ресурса не завершает редактирование и не заменяет документ.

### Ручной сценарий завершения прототипа

Создать пустую сцену; добавить видимый пол и три куба. Пол — Static, первый куб — Dynamic с gravity, второй — Dynamic без gravity, третий — Dynamic с выключенными столкновениями. Настроить размеры по контурам Collider. Через Play проверить падение и остановку на полу, неподвижность второго без внешних воздействий и прохождение третьего сквозь пол. Через Stop получить исходные Transform, selection и Undo/Redo. Изменить настройки и повторить запуск. Сделать Duplicate/Delete/Undo, Save As, закрыть и открыть сцену; данные должны сохраниться. Отдельно проверить Cancel при закрытии dirty-документа, неудачный Save и недоступный asset.

Для viewport проверить изменение размера, DPI, сворачивание, потерю фокуса, текстовый ввод и блокировку редакторских действий во время Play. Контуры должны совпадать с формой backend при поворотах, а не только в начальном положении.

## 8. Что отложить

- Новые графические backend, PBR и сложный material editor — до завершения M0/M1 и удобного размещения объектов.
- Async loading, job system и streaming — до измеренных задержек на реальных сценах. Избыточные обходы bindings исправлять локально, не начинать с переписывания AssetManager.
- Kinematic, force/impulse API, collision layers/masks, CCD, физические материалы и live editing — после устойчивого базового авторинга. Для Kinematic потребуется новый motion type и согласованный backend-контракт, одного `useGravity=false` недостаточно.
- Несколько документов, multiselection, полноценные prefabs, анимацию и универсальную reflection — после появления сценария, который оправдывает сложность.
- Иерархию и систему связей не вводить как обязательное условие обычного Collider.

Для воспроизводимости закрепить рабочий Windows/PhysX-профиль в CMakePresets и CI, затем добавить Jolt. Это сопровождение этапов, а не условие старта Physics Inspector. У `*.json` в .gitignore потребуются исключения для presets. Текущие поставляемые варианты basic shaders — Windows/D3D11 и macOS/Metal; наличие других значений в PlatformProfile не означает готовность остальных профилей.

План пересматривать после приёмки M0/M1: отмечать проверенные результаты и выбирать следующую потребность редактора по использованию конкретной сцены.
